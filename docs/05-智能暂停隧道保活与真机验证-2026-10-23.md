# 智能暂停隧道保活与真机验证

智能启停现在只暂停 Android 的系统引流，不停止已经建立的 SG 隧道。手机上已验证：系统没有 `tun0` 时，两节点仍能测速，后台维护继续运行；完全断网后恢复 Wi-Fi，也能在不打开引流的情况下恢复节点。手动停止时还发现了旧 WG 握手线程未停的残留问题，追加修复已进入自动验证，尚未在手机复测。

## 使用行为

不增加设置开关，也不修改已有 SSID、网段、账号、节点、订阅和覆写脚本。

| 操作 | 系统引流 | SG 隧道 |
| :---: | :---: | --- |
| 开启 VPN | 建立系统 TUN | 主动确保已勾选节点就绪 |
| 智能暂停 | 关闭系统 TUN | 保留套接字保护，继续维护与切网恢复 |
| 智能恢复 | 重建系统 TUN | 复用健康节点，不因引流变化重新授权 |
| 手动停止 | 停止，不自动启用 | 追加修复使用 WG Down 停止握手线程，保留配置与 IP 栈 |
| 再次手动开启 | 重新引流 | WG Up 恢复原设备，再检查节点 |
| 雅迪兼容暂停 | 兼容逻辑优先 | 撤销维护准入，不能由 SG 后台抢回引流 |

首页 SG 磁贴在智能暂停时显示节点数量和“引流已暂停”。Android VPN 未启动与 SG 两节点已连接可以同时成立；前者描述系统引流，后者描述独立隧道。

## 追加修复与待验项目

手动停止与智能暂停采用不同生命周期。智能暂停保留 JNI 保护回调；明确停止会撤销保护，所以必须同步停止 WG peer，不能只阻止拨号后任由定时器持续失败。

追加修复使用 WG `Down/Up` 而不是 `Close`，保留原设备、密钥和 IP 栈。初始化改为同步启动，避免缓冲的 `EventUp` 在停止之后才拉起 peer；重建提交前重新检查暂停与原生准入，丢弃越过停止边界的替换设备。TCP 接收线程固定使用本代 listener 和关闭通道，避免重开时读取下一代对象。

新增回归先因缺少 API 失败；真实 WG 反复启停又捕获异步启动和 listener 数据竞争。修复后，真实 WG、停止／恢复、停止期间禁止初始化及重建提交边界的定向 race 测试连续 10 轮通过；相关 core、outbound、config、dns、executor 回归通过。Android 产物与完整 CI 状态以之后的构建记录为准。

尚需用追加修复的最终 APK 完成：手动停止后静置、切网和重开不再产生持续握手失败，再启动能恢复节点，并复测智能暂停。手机已离线，本记录不把这些项目标为通过。长时间锁屏、真实基站漫游、跨天授权续期、雅迪前台和实际 ChatGPT 对话本轮也未重测。
