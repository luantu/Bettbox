# Bettbox 远程覆写与服务分流

手机使用远程脚本 `OpenAI-Google`，从 [overwrite-bettbox.js](http://172.18.34.110:44468/overwrite-bettbox.js) 下载。节点定义来自原订阅与飞连配置；脚本只引用这些对象，添加服务组和HTTP规则集，不包含机场服务器、密码、密钥或固定的订阅节点名单。原脚本保留停用，可用于回退。

## 分流与维护

| 代理组 | 有订阅时 | 无订阅时 | 健康探针 |
| :---: | --- | --- | --- |
| OpenAI 服务 | INT优先，再按原订阅顺序使用可识别支持地区的节点 | INT | chatgpt.com/cdn-cgi/trace，须200 |
| Google 服务 | 韩国优先，其余支持地区其次，INT最后 | INT | www.google.com/generate_204，须204 |
| Fuzhou-Node-1 | 保留原企业域名与服务器下发IP规则 | 相同 | 保留原内网HTTPS探针 |

HTTP规则直接引用服务器根目录既有文件，不新建平行清单，也不改它们的内容：

- OpenAI：`padavan_openai_domains.yaml`，手机加载29条。
- Google：`google_proxy_domains.yaml`，手机加载659条。
- 其余海外：`sg-node-overseas-no-google.yaml`，手机加载22721条，仍使用INT。

OpenAI、Google规则优先于通用海外规则，原订阅中的其他节点、组、规则和providers保留。原企业域名、内网IP和本机绕过规则随远程脚本保留。没有把混有大量普通国内域名的`rule-must_direct.yaml`整体引入福州组。

服务规则每24小时更新，下载使用DIRECT；服务器单IP的直连规则优先于企业私网引流。发布器从同一份OpenAI、Google YAML生成首启应急快照，无缓存且服务器故障时，两个服务仍有匹配规则。正常运行后HTTP文件继续更新，快照不会覆盖已下载内容。

两服务使用显式绑定对应组的DoH。机场节点服务器域名使用独立的引导解析，避免依赖尚未建立的自身服务组；企业DNS仍由福州WG使用服务器下发的内网DNS。手机既有“ChatGPT / OpenAI 自动使用INTL”已关闭，否则应用会在脚本执行后重新前置直指INT的规则，遮蔽fallback。两份Profile的全局脚本覆写均开启。

地区识别采用常用支持地区白名单，识别旗帜、中文/英文地区名和独立国家码。未知或多地区冲突名称、香港/澳门/中国大陆/俄罗斯、信息条目和内网WG不进入机场候选。该策略依据[OpenAI支持地区](https://help.openai.com/en/articles/7947663-chatgpt-supported-countries)与[Google AI支持地区](https://ai.google.dev/gemini-api/docs/available-regions)在2026-10-30的核验，属于保守候选筛选，不能证明某个出口IP已解锁所有产品。静态节点60秒探测、5秒超时；动态provider保留其既有检查周期。检查确认失败后，新连接选择后备节点，原请求可能需要重试。

## 真机验证

2026-10-30在原手机保留全部数据验证。测试从Mac通过ADB转发到手机本地mixed-port，流量由手机的Mihomo选择规则和出站；结果再由Bettbox“请求→详情”读取，不用Wi-Fi自身可直达目标代替隧道证据。

| 配置 | 请求 | HTTP | 已观察到的路径 |
| :---: | :---: | :---: | --- |
| 机场订阅 | ChatGPT trace | 200 | RuleSet(bettbox-openai) → OpenAI服务 → FZ-INT-Node → WG |
| 机场订阅 | Google generate_204 | 204 | RuleSet(bettbox-google) → Google服务 → 韩国MD1 |
| 机场订阅 | 原企业探针 | 200 | DomainSuffix(ruijie.work) → Fuzhou-Node-1 → WG；目标为内网IP |
| 本地SG，无机场订阅 | ChatGPT trace | 200 | RuleSet(bettbox-openai) → OpenAI服务 → INT → WG |
| 本地SG，无机场订阅 | Google generate_204 | 204 | RuleSet(bettbox-google) → Google服务 → INT → WG |
| 本地SG，无机场订阅 | 原企业探针 | 200 | DomainSuffix(ruijie.work) → 福州组 → WG，内网DNS请求亦观察到同一WG出站 |

最终Node行为测试17项通过，Go core全套测试通过。新增集成用例使用当前Mihomo实际parser验证provider过滤、伪装为支持地区的直连/DNS类型排除、首启HTTP503时保留快照、成功下载后更新失败保留已下载规则。另以真实HTTP响应和Mihomo健康检查、fallback代码验证首节点403、次节点200或204时选择后备；宽松的原provider探针随后运行也不会污染服务检查状态。最终脚本已再次同步，空配置及订阅配置三种请求均复测为200／204／200。

这次没有主动断开手机真实INT来测试所有机场出口，也没有登录或发送ChatGPT对话；普通Google探针不能证明Gemini账号可用。公网DNS验证覆盖配置和core解析逻辑，没有取得独立的手机DNS抓包；企业域名则实际解析为内网地址，并在请求记录观察到内网DNS经福州WG传输。

## 发布与回退

源脚本在`scripts/overrides/overwrite-bettbox.js`，发布器为同目录`build_service_bundle.py`。发布目录输入使用根目录两份原规则文件，以及从原覆写导出的私有`local-routing.json`，字段为`bypass`、`corporate`，每项是未带目标的classical规则。不要将私有文件提交公开Git。

```sh
python3 -m pip install -r scripts/overrides/requirements.txt
python3 scripts/overrides/build_service_bundle.py RULE_DIRECTORY OUTPUT_JS
node --test test/overrides/*.test.cjs
```

把生成包发布为服务器根目录`overwrite-bettbox.js`。手机“配置→脚本”选择`OpenAI-Google`；其菜单“同步”下载新脚本，规则资源页“同步”更新HTTP YAML。修改根目录规则不需要重编APK，也不需要把节点复制进脚本。变更SG内网路由时，应保留既有企业规则，重新生成发布包并读回验证。回退时选择原`CorpLink`脚本，并恢复原自动OpenAI设置。

本次没有修改APP功能或构建流程，不重编、不安装APK。提交使用`[skip ci]`跳过APK工作流。旧文件名已移出HTTP目录；手机条目仍能成功同步，确认使用更名后的入口。发布包SHA-256为`76dd2e0db1d869650f989a3eaa04c68839059ffbe5afeb019898e1b07299da5c`，服务器HTTP回读一致。

测试结束恢复原机场订阅、智能暂停与输入法，一分钟熄屏、原常亮设置、Wi-Fi开和蜂窝数据关；首页SG为2/2。没有改变原地点规则、账号、节点勾选或企业探针。临时ADB转发、界面XML、输入辅助JAR与本次导出文件已清理。
